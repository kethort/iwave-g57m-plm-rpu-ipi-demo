# PLM and RPU IPI Debug Build

This repository contains:

- A custom Versal PLM build with a user IPI module.
- An RPU Cortex-R5 ping-pong application.
- A Vitis automation script that creates the PLM and RPU projects, builds both applications, and can include the RPU ELF in the generated PDI.

## Prerequisites

- AMD Vitis 2025.2 installed and available as `vitis`.
- A compatible Versal XSA file.
- `bootgen` available from the Vitis installation.
- Git submodules initialized.
- In the Vivado design, enable the PL-side RPU IPI master for channel 1 so the
  RPU/PLM IPI path exists in the generated hardware handoff.

From the repository root:

```bash
git submodule update --init --recursive
```

## Repository source layout

The maintained source files are expected at:

```text
plm/
├── build-plm
├── build/                 # generated Vitis workspace, kept locally for debug
├── rpu-app/
│   ├── Cargo.toml
│   ├── bsp_bindings/
│   └── rpu_ipi_ping_pong/
│       └── src/
│           ├── main.rs
│           └── remoteproc.rs
└── src/
    ├── common/
    │   ├── xplm_ipi_ping_pong_module.c
    │   └── xplm_ipi_ping_pong_module.h
    └── ...other custom PLM source overrides...
```

The maintained source is `plm/src` and `plm/rpu-app`. The local `plm/build`
workspace and `plm/rpu-app/target` directory are generated outputs, but they are
kept in this lab checkout because the current debugger and remoteproc scripts
use their ELFs directly.

## Build the PLM and RPU together

Run this command from the repository root:

```bash
vitis -s ./plm/build-plm \
    ./plm/build \
    --xsa ./system.xsa \
    --custom-source-dir ./plm/src \
    --register-module xplm_ipi_ping_pong_module.h:XPlm_IpiPingPongModuleInit \
    --user-modules-count 1 \
    --rpu-source ./plm/rpu-app \
    --rpu-app-name rpu_ipi_ping_pong \
    --rpu-cargo-package rpu_ipi_ping_pong \
    --rpu-platform-name rpu_platform \
    --rpu-processor psv_cortexr5_0 \
    --rpu-domain standalone_psv_cortexr5_0 \
    --rpu-core r5-0 \
    --symlink-sources \
    --force-regenerate \
    --launch-vitis
```

This flow:

1. Creates or updates the PLM platform and application component.
2. Overlays the maintained PLM source from `plm/src` into the generated PLM component.
3. Builds the custom PLM ELF.
4. Creates the RPU platform for `psv_cortexr5_0`.
5. Creates the `rpu_ipi_ping_pong` application component.
6. Exposes the Rust workspace under the RPU Vitis component.
7. Builds the RPU ELF with Cargo and copies it to the Vitis component output.
8. Generates a combined PDI containing the custom PLM and RPU application.

## Regenerate only when needed

Use `--force-regenerate` when switching between stale/generated components,
changing the XSA, or repairing launch/debug metadata. For normal source edits,
the same command can be rerun without `--force-regenerate`:

```bash
vitis -s ./plm/build-plm \
    ./plm/build \
    --xsa ./system.xsa \
    --custom-source-dir ./plm/src \
    --register-module xplm_ipi_ping_pong_module.h:XPlm_IpiPingPongModuleInit \
    --user-modules-count 1 \
    --rpu-source ./plm/rpu-app \
    --rpu-app-name rpu_ipi_ping_pong \
    --rpu-cargo-package rpu_ipi_ping_pong \
    --rpu-platform-name rpu_platform \
    --rpu-processor psv_cortexr5_0 \
    --rpu-domain standalone_psv_cortexr5_0 \
    --rpu-core r5-0 \
    --symlink-sources \
    --launch-vitis
```

The generated Vitis RPU application component is only a debug/container component for the Rust firmware. With `--symlink-sources`, the generated component refers back to the maintained Cargo workspace under `plm/rpu-app`. The stale empty-application C template is removed by the build script.

## Expected build outputs

With the commands above, the important outputs are:

```text
plm/build/
├── platform/
├── plm/
│   └── build/
│       └── plm.elf
├── rpu_platform/
├── rpu_ipi_ping_pong/
│   └── build/
│       └── rpu_ipi_ping_pong.elf
└── ...generated PDI and BIF files...
```

Use the RPU ELF from the generated Vitis component when loading symbols in an RPU debug configuration:

```text
plm/build/rpu_ipi_ping_pong/build/rpu_ipi_ping_pong.elf
```

For the remoteproc flow, `scripts/load_remoteproc_elf.sh` loads the Cargo-built
Rust ELF by default:

```text
plm/rpu-app/target/armv7r-none-eabihf/debug/rpu_ipi_ping_pong
```

Use the PLM ELF generated by the PLM component for PMC/PPU symbols:

```text
plm/build/plm/build/plm.elf
```

Confirm the exact paths after a build with:

```bash
find plm/build -type f \( -name 'plm.elf' -o -name 'rpu_ipi_ping_pong.elf' -o -name '*.pdi' \) -print
```

## Rebuild after source changes

Edit only the maintained source directories:

```text
plm/src/
plm/rpu-app/
```

Then rerun the same `vitis -s ./plm/build-plm ./plm/build ...` command. Do not
edit generated files under `plm/build/`, because they may be replaced the next
time the workspace is generated.

## Clean rebuild

Remove only generated output:

```bash
rm -rf build plm/build plm/.Xil
```

Then rerun the build command.

Do not delete:

```text
plm/build-plm
plm/src/
plm/rpu-app/
```

## Debugging notes

### RPU included in the PDI

When firmware has already been loaded by the PDI, JTAG, or remoteproc, configure
both PLM and RPU debug launches as attach-to-running launches:

```text
Program device:        false
Reset entire system:   false
Reset processor:       false
Download application:  false
Stop at main:          false
```

Point the symbol file at the exact RPU ELF that was packaged into the programmed PDI.

For PLM/PPU source debugging, point symbols at:

```text
plm/build/plm/build/plm.elf
```

### Shared UART output

PLM and RPU may share the same UART. Simultaneous prints can interleave at the character level. Keep heartbeat logging disabled or infrequent and avoid printing from both processors at the same time when clean logs are required.
